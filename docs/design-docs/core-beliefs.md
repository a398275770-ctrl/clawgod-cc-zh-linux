# 核心信念（智能体优先的操作原则）

> 这是**争议的裁决依据**。出现"该不该这么做"的分歧时，回到这份文件，而不是回到聊天记录。
> 通用原则源自《Harness engineering: leveraging Codex in an agent-first world》（2026-02-11，OpenAI），本项目特有条目为改造与维护中沉淀的裁决。

## 通用原则

1. 人类掌舵，智能体执行。人类不直接贡献代码行。
2. 工程师的工作是设计环境、明确意图、构建反馈回路。
3. 上下文是稀缺资源；给地图，不给说明书。
4. 智能体在运行时看不到的东西，对它来说不存在。
5. 强制不变量，不微观管理实现。
6. 中央强制边界，本地允许自主表达。
7. 纠错成本低，等待成本高。
8. 技术债是高息贷款，小额高频偿还。
9. 遇到卡点先问："缺的是什么能力？如何让它既清晰可读又可强制执行？"
10. 人类品味要持续被捕捉——写进文档，或直接编码进工具。
11. 交互式决策必须落盘：确认过但不写进仓库的决策等于没做。
12. 改造存量项目时，重构不改变业务行为；行为变更必须显式登记并单独提交。

## 本项目特有裁决

13. **零 npm 依赖是特性，不是缺陷**（2026-10-12 D2）。不引入 `package.json`；lint、覆盖率、检查工具一律用 Node 内置能力自研。新增任何外部依赖必须先推翻本条并记录理由。
14. **翻译数据单一数据源**。`verbs/zh-CN.json`、`tips/zh-CN.json`、`cli-translations.json` 之外不允许出现第二份手写译文副本；派生配置现场组装，不预生成。
15. **`plugin/` 是负载副本，不是第二源码树**。只由 `sync-payload.sh` 从根复制；改 `plugin/` 副本的提交一律打回。
16. **sh/ps1 双实现是有意冗余**（2026-10-12 D3）。不为消除重复而合并；代价用「改动必须成对」的机械检查对冲。
17. **Patch 的第一优先级是"CLI 永远可用"**。汉化是增强，英文是可接受的降级态；任何 patch 失败路径都必须回滚到英文可用，不允许留下损坏的 CLI。
18. **Hook 等技术术语保留英文**。Hook、API、PR 等不翻译；追求准确优先于追求全中文化。
19. **对上游版本诚实**。未验证的版本窗口如实标注"未验证/本机自验证"，不夸大支持范围（见 README 与 support-matrix 的措辞约定）。
20. **跳过与豁免必须显式登记**：测试跳过、门禁豁免都要带原因与恢复条件（2026-10-12 D5），不允许静默跳过。

## 重构红线（R1–R8，每次改业务代码前必读）

以下八条是**硬约束**，不是建议。它们源自《存量项目 Harness 工程化规则》§9，因属于"用来约束日常的"规则而常驻于此（施工图已按 §14.3 归档）。

| # | 红线 | 落地含义 |
|---|---|---|
| R1 | **保留原有业务行为** | 重构的定义就是行为不变。改动前后对相同输入必须产出相同结果（用测试或对拍脚本证明）。 |
| R2 | **行为变更显式登记** | bug 修复与业务变更必须先在 `docs/exec-plans/tech-debt-tracker.md` 登记，并**单独提交**，不与重构混在一个 commit 里。 |
| R3 | **先护栏后动手** | 没有测试和门禁保护的模块，先补保护再重构。 |
| R4 | **不做范围外优化** | 发现的新问题登记进台账，不在本次提交里顺手处理。 |
| R5 | **不删无法判断的内容** | 存疑的文档/代码标注"待核实"并开 issue，不静默删除；删除操作须单独征求人类同意。 |
| R6 | **不引入不可内化的依赖** | 优先可组合、API 稳定、行为可推理的依赖（呼应 #13 的零 npm 依赖）。 |
| R7 | **不藏信息** | 关键决策必须落进仓库，不允许只存在于对话或人的记忆里。 |
| R8 | **每一步可回滚** | 每个批次都要有明确回滚方式，并写进计划。 |

> **配套契约**：计划先行（计划未获人工确认前不改业务代码）、阶段串行、不确定就提问（遇到无法从仓库推断的产品语义或业务意图，向人提问，不得自行猜测后改造）。

## 反模式（本项目真实踩过，2026-10 两轮改造实证）

1. **只写文档，不做机械校验**。文档会瞬间腐烂。能写成 linter 规则或结构测试的，就不要只写在文档里——文档只留"为什么"，"怎么做"交给工具。
2. **规则只写在一次性文档里**。施工图会归档，规则若没迁移进常驻文档，归档那天就是规范退化成口口相传那天。
3. **留着一个不启用的选项**。比没有更糟——它制造虚假的安全感（实例：`check-doc-links.js --strict` 从未接线，让人以为文档路径有门禁守护）。
4. **覆盖率数字不可信还在拿它做决策**。统计口径要把"同一份代码"只算一次（实例：`plugin/` 负载副本与根文件双计，把整体拉低 5.45pp）。
5. **门禁只查平均值，不查个体**。整体达标但单文件几乎没测，等于没有门禁（实例：`native-repair.js` 13.5% 长期无人告警）。
6. **测试/脚本创建临时文件不清理**。单次无害，累积会把磁盘或 inode 配额耗尽，之后**任何**创建文件的流程静默失败（实例：`mkdtempSync` 累积 10977 目录打满 tmpfs）。
7. **用手工 grep 做依赖分析就动手重构**。表达式里的裸标识符访问（如 `signature.exec(s)`）不在函数调用形态里，grep 抓不到——先用静态扫描工具，再用测试兜底。
8. **多个守护清单不同步**。新增一类文件往往要在多处登记（负载副本、指纹、payload 守护、测试 pairs），漏一处测试会报出来，但那是返工成本。
9. **用 `git reset --hard` 回滚实验提交**。它会把当时所有未提交的工作一起冲掉。实验性改动先备份到 `/tmp` 或先提交再 reset。
10. **管道命令里读 `$?`**。`cmd | head` 之后 `$?` 是 `head` 的退出码，不是 `cmd` 的——负向实测会得出相反的结论。
